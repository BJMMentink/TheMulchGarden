# God’s Eye View integration

## Current stage

The `World` carousel page embeds the genuine upstream God’s Eye View app, vendored under `vendor/gods-eye-view` from [bilawalsidhu/gods-eye-view](https://github.com/bilawalsidhu/gods-eye-view) (MIT license). It is not a visual re-creation. The page and its key-management API are restricted to signed-in `user` and `admin` accounts. The companion app independently checks the same HttpOnly Mulch Garden session before returning its document or serving its API routes, so hiding the navigation item is not the security boundary. Guests cannot open the app or query its runtime configuration.

For local development, `node server.js` starts Mulch Garden on its configured port (4173 by default) and the Vite companion on loopback port 4175. The embedded app uses the same hostname with a different port, so the host-scoped session cookie accompanies its member checks. The embed preserves God’s Eye's native side panels, layer filters, and POWER UP control. The “Keys” and “How it works” guides sit below the app.

Cloudflare Pages can serve the built static app from `/godseye/` on the same site origin. Its Pages Function checks the Mulch Garden session before returning app assets; the Worker provides the app URL and encrypted per-account key routes. The Pages project must use the God’s Eye build command and `_site` output described in `cloudflare/README.md`; its currently configured legacy build command does not include the globe app. The Cloudflare Worker does not yet implement God’s Eye's upstream live-data API routes, so Cloudflare is not full feature parity. For now, use the local companion to test live provider data. Never expose the Vite companion directly to the public internet.

The upstream package requires Node `>=24.14 <25` or `>=26 <27`. If its ignored `node_modules` folder is absent, install the vendored app's dependencies from `vendor/gods-eye-view` (for example, `npm ci` using the upstream lockfile), then start Mulch Garden from the repository root. No visitor downloads are required: the integrated application is delivered in the website iframe. Internet access is still needed for the app's remote assets and public-data sources.

## Provider-key behavior

The native `POWER UP` area saves Google Maps, OpenAI voice, AISStream, NASA FIRMS, TomTom, Cesium ion, OpenSky, and Launch Library keys separately on each account. The local companion reads only the signed-in member's key for supported provider routes. In the current Cloudflare build, keys are stored and browser-provider keys can be returned to that member, but the Worker does not yet implement God’s Eye's live provider routes or voice; don't assume a saved key makes those Cloudflare features operational. AISStream is also not wired to members' separate streams. The strict-$0 baseline enters no keys. A member's optional provider key can expose that member to a provider's usage charges; Cloudflare does not pay those provider charges.

Both the local Node API and Cloudflare Worker enforce authentication and scope each record to the session's user ID. The stored envelope uses AES-256-GCM with a fresh 96-bit IV for each save and authenticated additional data bound to the app, envelope version, user ID, and provider. The normal status API returns labels and configured/enabled flags only; the authenticated runtime API intentionally reveals enabled browser-provider keys only to their owning user's browser, where Cesium/Google need them. Browser-side map keys are visible to that user's browser and the provider; users should restrict keys by allowed website/API and quotas. The OpenAI key stays server-side.

Local development automatically creates `data/godside-key-encryption.secret`; `data/` is ignored by Git. This is a local-development convenience, not strong protection against full-device compromise because the local key and ciphertext live on the same computer. The Node preview stores users and app data in local JSON files, not Cloudflare D1. A first local admin can be created only from a loopback connection while that store is empty; its password is hashed and setup closes once an account exists. Production requires a separate Worker secret named `GODSIDE_KEY_ENCRYPTION_SECRET`, encoded as base64url from 32 random bytes. Never put it in source, D1, browser runtime config, logs, or chat. Back it up securely: losing or rotating the secret without re-encrypting existing records makes them undecryptable.

The Cloudflare integration source includes the Pages asset gate, same-origin app route, and D1-backed encrypted native-key endpoints. Apply `cloudflare/migrations/0005_add_godside_provider_keys.sql` to an existing D1 database (fresh installs use `cloudflare/schema.sql`) and set the Worker secret through Cloudflare's secret manager when preparing a deployment. The Worker does not run the local Vite companion, OpenAI resolver, or upstream live-data routes, so saved Cloudflare keys currently do not activate those feeds or voice. In particular, the hosted version currently has no camera catalog/frame/HLS proxy route; do not count on Cloudflare CCTV functionality yet.

## Free-tier and provider boundaries

As checked on 2026-10-05, Cloudflare Workers Free includes 100,000 combined Workers/Pages Function requests per day, resetting at midnight UTC, and 10 ms CPU per invocation. The member gate in `functions/godseye/_middleware.js` runs for each request under `/godseye/`, including app assets, so those protected asset requests invoke a Pages Function; a static request is free/unlimited only when it does not invoke a Function. Its auth lookup is a Worker subrequest, which Cloudflare says is not separately billed as an inbound request. D1 Free includes 5 million rows read/day, 100,000 rows written/day, and 5 GB total storage. Free limits stop/reject excess work; they do not automatically move the account to a paid plan. The Cloudflare app allows one owner/admin plus up to three members. For that small audience, ordinary logins and key-status reads are far below the daily limits; repeated page reloads multiply the protected-asset Function count. Check Cloudflare's usage dashboard rather than treating this as a guarantee.

Those hosting limits do not make external APIs free. The bundled God’s Eye docs currently identify: NASA FIRMS free map keys with a 5,000 transaction/10-minute limit; TomTom's current no-card free plan with 200,000 Flow/Incidents vector-tile requests/month (over-limit requests return 429); Launch Library 2 with 15 free unauthenticated requests/hour; Cesium ion Community as $0 only for eligible individual personal/non-commercial use and finite quotas (currently 1,000 Google Photorealistic root tiles/month and 15 GB streaming/month); AISStream as advertised free but without formal terms documented; and OpenSky as restricted to research/non-commercial purposes. Google Map Tiles requires billing: its Photorealistic 3D SKU currently has 1,000 no-cost billable tile events/month, with additional returned tiles billed by use. The renderer may request many tiles; Google's published daily root-tile quota is not a monthly spend cap. For a guaranteed $0 baseline, keep this key empty. OpenAI voice/summaries are usage-billed. Treat provider limits and prices as changeable. Never enable provider billing on behalf of a user.

The keyless baseline also uses public/open or community data such as Esri/OSM map paths, NOAA weather, USGS seismic data, CelesTrak, and public transport/camera feeds. These currently need no provider API key in the bundled app, but “no key” does not mean unlimited or unconditional: public services can require attribution, limit interactive use, restrict commercial use, change access, or go offline. Open-Meteo is used for some cockpit weather; its no-key free API is limited to non-commercial use, currently 10,000 calls/day, with no uptime guarantee. The current hosted Cloudflare build does not proxy every upstream feed, so features unavailable there should not be mistaken for extra provider usage.

## Camera loading and request budget

The bundled CCTV panel and data layer start off. Opening the page does not fetch a camera catalog or camera frame unless a shared scene explicitly turns the layer on. When the member turns it on, the local companion fetches camera metadata/catalogs, but does not download a still for every listed camera. The ambient layer caps visible camera cards at 20–40 based on zoom, caps the cold-start burst at four in-flight frame requests spaced 250 ms apart, then permits at most one ambient-card fetch per second. Ambient stills refresh on conservative source-aware intervals (typically 3–5 minutes; Fintraffic uses 10 minutes). The selected camera preview can refresh every 10 seconds while active; idle cameras use a 60-second cadence. Auto-hop starts off. The live-video implementation caps two simultaneous sessions and is lazy, but this implementation lives in the local Node companion—not the current Cloudflare Worker.

Accordingly, a first visit to the Cloudflare God’s Eye route does not start CCTV work. CCTV still/video feeds are not yet supported by the hosted Worker. When/if those endpoints are added, they should preserve the upstream client pacing and add per-account daily request/byte caps and an admin kill switch before being exposed. Public camera feeds are third-party sources: local use may consume their bandwidth and is subject to each source's terms, but frame traffic is not presently served by Cloudflare in this integration.

The strict-$0 Cloudflare baseline therefore means: keep optional provider keys absent unless a member deliberately supplies one, leave Google/OpenAI off unless the member has independently set provider quotas and accepts possible charges, and keep any future Cloudflare camera proxy behind bounded, user-triggered requests. It cannot guarantee third-party services will remain free.

## Relevant files

- `src/app.js`: carousel, member navigation, and guest/member/admin access boundary.
- `src/godside.js`: panel markup and key-form/status behavior.
- `src/godside-crypto.js`: shared provider allowlist and authenticated encryption.
- `vendor/gods-eye-view`: actual upstream app and its package manifest/lockfile.
- `server/godside-view-server.js`: starts the loopback-only Vite companion and strips global provider keys.
- `vendor/gods-eye-view/server/standalone/mulch-garden-integration.js`: per-request session gate and user-scoped provider-key context.
- `server/controllers/godside-keys-controller.js`, `server/lib/local-encryption-secret.js`: local API and dev key lifecycle.
- `cloudflare/src/index.js`, `functions/godseye/`, `cloudflare/migrations/0005_add_godside_provider_keys.sql`: Cloudflare app route, member-only static-asset gate, and D1 storage.
- `public/_headers`: site-wide CSP and microphone policy; the Cloudflare app route adds its same-origin frame policy.

## Provider integration checklist

Before activating a provider, separately review current terms, pricing, quotas, required attribution, referrer restrictions, and whether the user's requested free-only boundary can be enforced. Keep keys per-user. Never send OpenAI keys to a browser. Prefer a server-side proxy for secrets; if a provider requires a browser key, explain that it is visible to that user's browser and require provider-side restrictions. Add a hard quota/cost-control path where the provider supports it, test both local and Cloudflare backends, and update this document. Cloudflare still needs authenticated implementations of the upstream provider APIs before those features can be exposed there.
